# Проблемы и риски текущей архитектуры InsureTech

## 1. Высокая зависимость сервисов от синхронных REST-вызовов

Сервисы `core-app` и `ins-comp-settlement` получают данные о продуктах и тарифах через синхронные REST-запросы к `ins-product-aggregator`.

Это создаёт следующие проблемы:
- увеличение времени ответа при медленной работе внешних API;
- каскадные задержки между сервисами;
- рост количества таймаутов и ошибок при увеличении нагрузки;
- снижение отказоустойчивости системы.

---

## 2. Рост количества страховых компаний увеличит нагрузку на систему

Сейчас `ins-product-aggregator` обращается к пяти страховым компаниям. В будущем их количество увеличится до десяти и более.

Это приведёт к:
- увеличению количества внешних запросов;
- росту времени агрегации данных;
- повышенной нагрузке на `ins-product-aggregator`;
- ухудшению производительности всей системы.

---

## 3. Нестабильность внешних API влияет на работу внутренних сервисов

При ошибках или медленных ответах со стороны страховых компаний:
- `ins-product-aggregator` может не успевать собрать данные;
- внутренние сервисы не смогут получить актуальные тарифы;
- оформление страховок может завершаться ошибками.

Таким образом, внешние системы становятся критической точкой отказа.

---

## 4. Использование периодического polling создаёт лишнюю нагрузку

Сервис `core-app` обновляет данные каждые 15 минут, а `ins-comp-settlement` — один раз в сутки.

Недостатки такого подхода:
- данные могут быть неактуальными между обновлениями;
- создаются лишние запросы даже при отсутствии изменений;
- система медленно реагирует на обновление тарифов и продуктов.

---

## 5. Высокая связность сервисов

Сервисы напрямую взаимодействуют друг с другом через REST API.

Это приводит к:
- сложностям при масштабировании;
- увеличению количества точек отказа;
- усложнению развития архитектуры;
- необходимости учитывать доступность каждого сервиса при выполнении операций.

---

## 6. Риск потери данных при обмене между сервисами

Сейчас обмен данными между сервисами выполняется напрямую через REST.

При временной недоступности сервиса:
- запрос может завершиться ошибкой;
- данные могут быть потеряны;
- потребуется повторная обработка вручную или через retry-механизмы.

---

# Предлагаемое решение

Для снижения связности сервисов и повышения отказоустойчивости предлагается перейти на Event-Driven архитектуру с использованием брокера сообщений (Kafka или RabbitMQ).

Основные изменения:
- заменить часть синхронных REST-взаимодействий на асинхронный обмен событиями;
- использовать события для передачи информации о продуктах, тарифах и оформленных страховках;
- внедрить паттерн Transactional Outbox для гарантированной доставки событий;
- сократить количество прямых зависимостей между сервисами.

Такой подход позволит:
- повысить отказоустойчивость;
- уменьшить влияние медленных внешних API;
- улучшить масштабируемость системы;
- снизить нагрузку на сервисы;
- обеспечить более быстрое обновление данных.

# Transactional Outbox

Используется для гарантированной доставки событий в Kafka без потери данных для core-app и ins-product-aggregator.
